# UI 适配器升级工程

本目录是 `antdv-superform` 下一阶段 UI 框架解耦工程的事实来源，与 `docs/` 文档站分离。这里记录架构边界、已接受决策、阶段任务、当前状态、验证要求和迁移影响，避免长期开发依赖聊天上下文。

## 阅读顺序

开始任何升级任务前，按以下顺序恢复上下文：

1. [ARCHITECTURE.md](./ARCHITECTURE.md)：确认目标架构和不可跨越的边界。
2. [status/CURRENT.md](./status/CURRENT.md)：确认当前阶段、临时状态和下一步。
3. 与任务相关的 `design/` 文档：理解具体模块如何改造。
4. `decisions/` 中相关 ADR：确认已经接受的设计决定。
5. [plans/MASTER.md](./plans/MASTER.md)：只执行当前阶段内的任务。
6. [verification/TESTING.md](./verification/TESTING.md)：按阶段要求验证。
7. [migration/BREAKING-CHANGES.md](./migration/BREAKING-CHANGES.md)：检查是否产生用户可见变化。

## 文档职责

| 位置 | 职责 | 更新时机 |
| --- | --- | --- |
| `ARCHITECTURE.md` | 描述最终架构、依赖方向和长期不变量 | 架构目标发生变化时 |
| `design/` | 描述模块设计、职责拆分和能力映射 | 进入对应阶段前或设计调整时 |
| `decisions/` | 记录已经接受的关键决策及后果 | 做出或推翻架构决策时 |
| `plans/MASTER.md` | 记录阶段范围、任务、非目标和验收条件 | 任务推进时 |
| `status/CURRENT.md` | 保存新会话恢复工作所需的最小状态 | 每个阶段任务完成后 |
| `verification/` | 记录验证策略与阶段验证结果 | 测试边界变化或执行验证时 |
| `migration/` | 记录用户可观察的不兼容变化及迁移方式 | 公共 API 或行为改变时 |

## 完成协议

阶段任务不能以“代码已经修改”作为完成标准。完成前必须依次确认：

1. 实现符合当前计划范围和 ADR。
2. 相关测试已补充并通过。
3. `plans/MASTER.md` 的任务和验收项已更新。
4. `status/CURRENT.md` 已反映真实项目状态。
5. 新架构决策已写入 ADR。
6. 用户可见变化已写入迁移记录。
7. 阶段产生可人工验证的 UI 行为时，已在 `upgrade-dev/pages/` 添加或更新对应测试页面，并登记到页面清单。
8. 已检查 Git diff，未夹带计划外修改。

日常开发只运行相关测试和 lint；`build` 仅在确认提交、准备提交时执行，遵循根目录 `AGENTS.md`。

## 阶段切换与新增需求

阶段标记完成不代表自动获得下一阶段的实施授权。阶段完成后，对话中出现改变或增加需求时，按以下顺序处理：

1. 先分析需求影响范围、与已接受决策的关系以及是否改变阶段验收结论，并向用户确认。
2. 影响已完成阶段实现或验收结果的，在该阶段下新增“回补子任务”，完成并重新验证后再恢复完成状态。
3. 不属于已完成阶段，但必须在下一阶段开始前完成的，在下一阶段下新增“前置子任务”，获得明确执行指令后处理。
4. 已明确归属于更后阶段的，只更新对应阶段的任务、依赖或验收条件，不提前实现。
5. 只有用户明确要求“开始”或“继续”某个阶段后，才能实施该阶段任务；更新计划、状态和影响分析本身不视为开始实施。

`status/CURRENT.md` 应区分“已完成阶段”“待启动阶段”和“正在实施阶段”，不能因为上一阶段完成就自动把下一阶段写成正在执行。

## 任务完成后的记录规范

任务完成后，应把信息更新到对应的事实来源，不额外为每个任务创建重复的“完成记录”文件。

| 信息 | 记录位置 | 记录内容 |
| --- | --- | --- |
| 任务进度 | `plans/MASTER.md` | 勾选完成项、验收结果、延期项及原因，并在对应阶段追加简短进展记录 |
| 项目状态 | `status/CURRENT.md` | 已完成能力、当前阶段、临时实现、已知问题、下一项任务 |
| 验证结果 | `verification/TESTING.md` | 执行的命令、结果、未执行项及原因、剩余风险 |
| 架构决策 | `decisions/` | 新决策或对既有决策的变更、原因与后果；普通实现细节不写 ADR |
| 用户可见变化 | `migration/BREAKING-CHANGES.md` | 以前和现在的用法、影响、迁移步骤、兼容策略及移除版本 |
| Dev 人工验证 | `upgrade-dev/pages/` | 阶段完成后增加对应测试页面，并在 `upgrade-dev/pages/index.ts` 登记入口 |

不记录 Git 已经能够准确表达的机械信息，例如修改了哪个文件的哪一行、删除了哪个 import。工程文档重点记录设计原因、状态变化、兼容影响、验证结论和下一步。

只有当单个阶段持续时间较长、跨越多个模块或多次提交，并且需要多个会话协作时，才把对应阶段从总计划拆成 `plans/active/Pxxx-阶段名称.md`；拆分后总计划只保留摘要、状态和链接。

## Dev 改造验证入口

运行 `pnpm dev:upgrade`，访问 `/upgrade-dev/index.html`。该入口与现有 `/index.html` 示例完全分离，只用于升级阶段的人工冒烟和交互验证。

每个产生 UI 行为的阶段完成后：

1. 在 `upgrade-dev/pages/` 新增或更新对应页面。
2. 在 `upgrade-dev/pages/index.ts` 登记阶段、标题和说明。
3. 页面应聚焦本阶段验收点，不复制完整示例站。
4. 自动化测试仍放在根目录 `tests/`；Dev 页面不能替代单元测试。
